# ORBIT — six-worker parallel execution protocol

**Established 12 November 2026 by owner instruction.** This is an **operations/coordination contract, not a second roadmap**. Product scope, dependencies, and BP statuses remain exclusively in [the master BP-00–BP-16 roadmap](../plans/ORBIT_POST_2_4_EXECUTION.md). This document describes six active ChatGPT worker conversations coordinated by a seventh, non-implementing commander conversation.

## Owner mandate and authority

The owner wants **six separate, simultaneously active developer chats** inside the existing ORBIT ChatGPT Project, with a **seventh commander chat** for prioritization, architecture review, scope arbitration, integration, and accurate progress reports. The commander is *not* Worker 1. The initial browser-side assembly has not been performed by this documentation PR: do not represent worker chats as launched just because these files exist.

The four workers are empowered to do substantive engineering end to end, not merely propose tiny low-risk changes. They may challenge weak assumptions; perform rigorous product, security, accessibility and architecture critiques; research official documentation, maintained examples, independent design references and licenses; explore radical but justified alternatives; add/refactor modules; significantly change UX while preserving ORBIT's spatial identity; build tests; open and merge source PRs after the defined quality gates. Treat prior design decisions as revisable hypotheses except the current owner's express privacy, recovery, spatial-identity and release requirements. **Do not choose the smallest or least ambitious patch merely because it seems safe.** Choose the highest-value READY work supported by evidence, make a reversible experiment where feasible, and report adverse findings honestly.

Use **task-relevant installed skills proactively**. Inspect the skill catalog and read the most specific matching skill before working. Apply skill workflows rather than naming them ceremonially. Search the repo before inventing new code; verify current upstream APIs, product references, cost and licenses on the web when material. Compare alternative approaches and run a critical self-review before requesting merge. No needless package/framework rewrite: large architecture changes need a measured reason and compatibility plan.

Broad delegated authorization covers ordinary code and docs edits, feature branches, tests, security research using nonprivate/synthetic data, architecture or UI refactors, non-destructive experiments, PR creation, reviewing exact diffs, merging green non-conflicting **source** PRs, and reviewing protected Preview deployments. **It does not silently authorize** data deletion or migration, changes to hosted SQL/RLS/Auth/Storage, access to privileged credentials, public publishing of formerly private data, paid providers, removal of Preview protection, or Production/domain/alias changes. Those require explicit, separately scoped owner approval, an evidence-backed recovery plan and release gates. Source merge is never proof of Production release or signed-in acceptance.

## Git integration and merge discipline

1. At session start re-read `AGENTS.md`, `CHATGPT_HANDOFF.md`, `docs/CURRENT_STATE.md`, this protocol, the assigned worker file, relevant source/tests, and query **actual** main/PRs/CI. Historical handoffs do not supersede GitHub.
2. Use worker-prefixed branches such as `feat/orbit-wN-<slice>` (`N` 1–6; or `fix/`, `perf/`, `docs/`, `test/`, `ci/` counterparts), always from freshly verified main. Open a single focused PR per testable slice titled `[W1] ...`, etc. Preserve immutability of V6/M1 historical manifests. Update the reviewed M2 source manifest with all touched hashed sources before final check.
3. Run focused tests and required CI. Review **all four required exact-head statuses**: `static-quality`, `local-postgres-rls`, `production-artifact-dry-run`, `unauthenticated-protection`. A previous head's greens do not apply after pushing. Inspect actual diff and security/backup/compatibility risks. Do not manually rerun green workflows for decoration.
4. Source-merge only when exact-head checks pass, no unresolved blockers, and changes are non-conflicting with other ongoing PRs. Where concurrent branches touch the same file, coordinate merge order and rebase/update source manifest; no blind force-push of protected main. If uncertain, defer merge to commander review, **not implementation**.
5. Default to synthetic fixtures and redacted logs; never put private journal/image bytes, authenticated signed URLs, sessions or secrets into source/CI artifacts. Protected Preview may be used for authorized validation, but differentiate synthetic vs signed-in owner vs physical-device evidence.
6. **W5 is the sole author of shared canonical documentation and derived progress reporting** (`docs/CURRENT_STATE.md`, `docs/PROGRESS.md`, `CHATGPT_HANDOFF.md`, the single master roadmap, changelog/release notes), under Command HQ review and merge arbitration. The Commander owns only its own HQ handoff and integration decisions; W1–W4 and W6 update only their own handoffs and PRs. If W5 is unavailable, other workers leave proposed corrections as PR/issue comments, not conflicting canonical edits; they continue independent source work.

## Predecessor-activity check before any replacement takes ownership

**Owner-reported incident:** After the owner was advised to immediately replace inaccessible W1/W2 chats, the original worker branches were still advancing. The new workers correctly inspected GitHub and avoided racing their predecessors. A conversation that cannot be reopened is **not evidence** that its active turn has stopped; a PR or running CI is **not proof** that a conversation is still running.

1. **Commander decision comes before the owner prompt.** If a worker chat is inaccessible, first inspect live `main`, the assigned worker's open PRs/branches, recent commits/PR updates/review comments and exact-head GitHub Actions. Compare observed timestamps (UTC) across at least a short check interval when practical, without making the owner wait for extended CI. Only then recommend **WAIT / READ-ONLY RECOVER / SAFE REPLACEMENT**. Never say "create a replacement immediately" before that check.
2. **Recent same-lane progress means WAIT for its write lane.** A same-worker branch push/PR edit within roughly the past 10 minutes, a just-created PR, or running CI suggests *possible* ongoing predecessor work; treat the relevant branch/files as occupied. Tell the owner what was observed and when, rather than pretending to know the ChatGPT chat's actual execution status. If the old chat is inaccessible, a replacement may **read/recover status only**, or independently work on a genuinely non-overlapping READY slice.
3. **Replacement starts with collision discovery.** Before editing, the replacement rechecks `main`, all open same-worker PRs, recent branches/commits, check runs, and the worker's own handoff. If the predecessor has an active PR, do not reimplement that slice, edit/push the predecessor's branch, close/merge it unilaterally, or touch overlapping source/test/manifest paths. Record the discovered PR/head in the recovery answer.
4. **Use one active writer per shared file.** If there is demonstrably independent READY work, create a distinct branch from verified current `main` with disjoint source and tests, and coordinate any shared `M2_SOURCE_MANIFEST.json` edits during integration. A new chat may resume an old stalled branch **only after** establishing no competing writer and documenting its intent in a PR/issue comment. GitHub signals alone can never prove a chat is dead; preserve unmerged changes rather than force-pushing.
5. **If no safe independent task exists, checkpoint and stop.** Report **WAIT** (including the exact observed PR and CI state) and give a read-only follow-up/recovery prompt. Recheck later on the owner's next active turn. Never create new work merely to keep a replacement busy, and never promise automatic continued work after this turn.

This is a **soft coordination lock**, not a new hosted lock service or an automated scheduler. Keep W1/W2/W3/W4 file ownership, GitHub review gates, and the commander's role distinct.

## Optional owner-facing work previews

The owner likes to **see meaningful work occasionally**, but explicitly does **not** require a preview on every update or for tasks with nothing visual to show. Choose previews when they genuinely clarify design, behavior or acceptance; do not let them slow security/reliability work or trigger extra CI/deployments.

- **UI/experience work (often W3):** For a meaningful change to a gallery, editor, navigator, theme, spatial layout or interaction, consider one or two **synthetic-data screenshots** (desktop/mobile or before/after), a short silent interaction clip/GIF, or a link to an **already-existing, access-controlled Preview**. Explain what changed and what is still unverified. Use `docs/DESIGN_EVIDENCE_PLAN.md` fixtures and screenshot artifacts when available; prefer a view the owner can actually inspect. A private, protected Preview is **not** permission to bypass sign-in or deploy to Production.
- **Backend/security/performance work (often W1/W2/W4):** Do not manufacture a UI preview. When it adds clarity, offer a small benchmark chart, sanitized mock restore flow, decision diagram, test result, or source/PR diff. Otherwise a concise source/CI summary is sufficient.
- **Privacy and evidence:** Only dummy/disposable content in screenshots, recordings or public GitHub artifacts. Never include owner journal text, private images, real account identifiers, OAuth fragments, signed Storage URLs, tokens or other private data. Do not expose private hosted deployments or change access controls just to enable a preview.
- **Presentation standard:** Label evidence **synthetic**, **protected Preview**, or **real owner/device verified** accurately. Link exact PR commit, screenshot artifact or accessible Preview URL; never claim a render or preview exists until verified. If a meaningful visual cannot be produced safely at the current step, say so briefly and move on.

The goal is periodic, useful visual visibility—not a compulsory media artifact and never a substitute for CI or owner acceptance.

## Required owner-assisted acceptance without artificial blocking

The owner explicitly permits workers to **ask for real-user testing when necessary**. Treat this as an available execution tool, not as a reason to stop development indefinitely.

- First finish every test possible with synthetic accounts/data, local/disposable DBs, protected previews and automated UI/CI. Then request owner testing **only for what cannot be verified responsibly without their device, signed-in identity, second controlled account, or a separately authorized operation**.
- A good request is concrete and bounded: protected URL / exact source SHA, 3–6 safe steps, dummy data, expected observations, what evidence to return, privacy instructions, and one decision that will unlock the next stage. Never ask for passwords, tokens, private journal data or screenshots containing identifying content.
- W6 prepares and coordinates a short acceptance checklist; W1–W4 can request it directly when needed (with W6 copied via issue). The owner should not be repeatedly asked for checks that synthetic fixtures can already prove.
- A pending owner acceptance gate blocks **claiming VERIFIED, Production promotion or risky hosted operations**, not completing independent source improvements, tests, UX refinements or the next safe READY slice. Record `OWNER ACCEPTANCE PENDING` and continue other work.
- When a worker discovers a concrete gate requiring owner action, ask rather than silently leaving it open. Clearly explain why the owner is uniquely needed; distinguish approval of an irreversible/hosted action from simply requesting a user-observed test.
- Real-device screenshots, short clips and screen recordings are optional, valuable when privacy-safe and useful; do not force visuals at every update.

Each BP row requires a timestamped verification basis and next gate; status is never inferred from a merged PR alone.

- `CHANGELOG.md`: historically ordered **verified released changes**, plus a clearly separated *Unreleased source* section only when sourced to exact merged PRs and explicitly labeled **NOT DEPLOYED**.
- `RELEASE_NOTES.md`: concise redirect/entry point for the **current shipped** product and archived V6 notes; historical details stay recoverable under versioned docs/commits.
- **GitHub Releases**: the official user-facing release records with tags, notes, source SHA and verified Production deployment. No GitHub Release for a source-only merge, and no public release announcement or tag that falsely implies Production without reviewed evidence and owner authorization.
- Git branches are disposable *pointers*, not the source of truth for completed work. Audit all branches against open PRs, ahead/behind ancestry, meaningful unmerged commits, rollback and active predecessor activity before any deletion. Never bulk-delete current branches from branch names alone. W5 prepares a reviewable batch; deletion/auto-delete settings require appropriate owner confirmation and an available supported GitHub capability. See `docs/REPO_HYGIENE_POLICY.md`.

## Proactive time-budgeted recovery (owner report: inaccessible chats after long turns)

**New owner-observed failure mode, 12 November 2026:** Some ChatGPT worker/commander conversations became impossible to reopen after a long uninterrupted response, reportedly around 20 minutes, sometimes largely spent waiting for GitHub Actions even though the context window was not full. **20 minutes is an operational warning, not a verified ChatGPT cutoff or guaranteed timer.** The existing context-limit handoff below is insufficient on its own. Apply these rules on **every active turn**, even with ample context remaining.

1. **Bound the current turn, not the whole task.** At turn start, capture a clock time when an available clock can provide one. Recheck elapsed time before expensive tool sequences, after major work phases and whenever CI is pending. Do not pretend to have a reliable stopwatch if the runtime exposes none; in that case, use small bounded work batches and checkpoint more conservatively. Aim to finish each uninterrupted assistant turn **within 15 minutes**, leaving a safety margin under the owner's observed ~20-minute failure window. This is a best-effort target, not a platform guarantee.
2. **Checkpoint early, not at the cliff.** By roughly **8–10 elapsed minutes**, after a material change, and **before starting any long GitHub Actions wait**, persist a recoverable record: committed/pushed branch or PR where appropriate, exact SHA, touched paths, test/CI status explicitly PASS/FAIL/PENDING/NOT RUN, unresolved risks, next concrete step and rollback. Never rely on an unpushed local worktree or chat transcript as the only copy of meaningful work. An incomplete/unsafe atomic operation must be made safe before stopping; do not force an unsafe commit or merge merely to satisfy the clock.
3. **Cut over no later than ~12–15 minutes.** Stop initiating new multi-tool features, deep research, or new CI waits. Save the worker's *own* GitHub handoff (`docs/handoffs/ORBIT_Wn.md`) or the commander's `docs/handoffs/ORBIT_COMMAND_HQ.md`, provide an independently useful final answer with current PR/branch links and **a fully copyable, worker-specific continuation prompt**, and end the turn. A user can paste that prompt in the same accessible chat or a fresh chat in the ORBIT Project. The replacement must validate live GitHub before continuing.
4. **Never hold a chat open merely to watch CI.** Poll at most a couple of times in a short bounded interval. If any of the four required exact-head checks is still running/queued, label the head **CI PENDING** with the run/PR link, save the checkpoint, give the continuation prompt and finish. GitHub Actions runs independently of the chat; a later active turn rechecks status. Never infer PASS, change an approval gate, or merge based on partial/outdated checks. A failed check gets its own next-action diagnosis, not an endless wait loop.
5. **Avoid invalidating already verified heads.** Adding a documentation/handoff commit to an open **source PR** changes its head and invalidates its previously verified exact-head CI. If tests already passed on that head, prefer a PR comment/update (which does not change the SHA) plus a **separate** narrowly scoped handoff-docs PR when needed. If tests have not started, the worker may include its own handoff in the source PR and then run CI against the final head. The commander owns shared coordination docs; no worker modifies another worker's handoff.
6. **Surface the handoff without depending on the old chat.** Every early-stop/final checkpoint must include: role (Commander or W1–W4), repository, status, latest verified branch/PR/head, precise next action, what must **not** be done, and a copyable new-turn message. Do not merely write 'continue' or tell the owner to invent instructions. If GitHub writing is temporarily unavailable, print the complete checkpoint and recovery prompt in the response, explicitly mark it **NOT PERSISTED**, and stop safely.
7. **No background-work claim.** A concluded ChatGPT chat does not continue autonomously, wake when CI turns green, or send to peer chats by itself. 'Autonomous worker' means working through successive READY tasks **while the user keeps its conversation active**, with durable GitHub state between turns. The commander may communicate via GitHub artifacts, but these are not guaranteed to be read by another open chat until it refreshes them.

**Minimum final-turn recovery block for workers** (populate actual values; do not leave placeholders in the owner-facing result): `ORBIT Wn | status | current PR/branch/HEAD | 4 CI checks (exact head) | last durable artifact | next file-level action | required owner gate, if any | COPY/PASTE CONTINUATION PROMPT`. For the commander, use `ORBIT Command HQ` and its checkpoint file. **A normal session ends with an actionable checkpoint; it does not have to approach context exhaustion to do so.**

## Continuity when chats reach context or length limits

A conversation is **not** a durable task database and cannot restart itself. Before a major phase transition, after a merge, or when nearing context limits, the worker must update **only its own** file `docs/handoffs/ORBIT_W1.md`–`W4.md`, on an active source PR or its own small docs PR. Preserve short, evidence-linked checkpoints rather than copying the entire chat.

Each checkpoint must state:
- **Objective and actual state**: NOT STARTED / ACTIVE / PR OPEN / SOURCE MERGED / BLOCKED; date, exact main SHA, work branch and current head.
- **What changed**: filenames, constraints, critical invariants, important design rationale, experiments rejected.
- **Evidence**: PR URL, four exact-head CI conclusions/run links, targeted test commands/results, synthetic vs owner/physical checks.
- **Pending**: open review comments, blockers/approvals, cross-worker contracts, no-touch paths.
- **Next executable action**: one exact file-level action; commands/tool queries to reproduce; rollback method.
- **Security**: no private tokens, signed URLs, user data or transcript dumps. Mark unknown outcomes **UNKNOWN**, not PASSED.

If a worker chat fills up: (1) finish or park its current atomic edit; (2) save the checkpoint and ensure its last Git commit/PR is durable; (3) create a **new chat in the same ORBIT ChatGPT Project**, titled `ORBIT Wn — <role> (continuation 2)`; (4) paste the recovery prompt below. The new chat independently re-queries live repository state and uses the checkpoint as an index, never as present truth. The commander can inspect PRs/handoff files to arbitrate; it cannot automatically see or send into other private chats from this session.

**Universal recovery prompt:**
> You are ORBIT Worker Wn continuing after a context rollover. Work inside `DoorBlox/orbit`. First inspect current `main`, open PRs, required CI and `AGENTS.md`. Read `docs/ORBIT_PARALLEL_COMMAND_PROTOCOL.md`, `plans/ORBIT_POST_2_4_EXECUTION.md`, `CHATGPT_HANDOFF.md` and `docs/handoffs/ORBIT_Wn.md`. Resume from the final checkpoint's next executable action after verifying it is still necessary; do not repeat merged work or reset earlier branches. You have the owner's broad source-engineering/design authorization stated in the protocol; use matching skills, research current references, be critical, implement and test real changes, maintain your own checkpoint. No silent Production/hosted-security/destructive/paid action.
