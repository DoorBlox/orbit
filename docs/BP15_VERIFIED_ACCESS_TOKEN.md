# BP-15 — offline asymmetric OAuth access-token verification (source only)

**12 November 2026 — security foundation, not a remotely reachable MCP server.** The module `server/mcp/jwt-access-verifier.mjs` is an offline, Node-only verifier designed to feed `createPrivateMcpReadBoundary({verifyAccessToken})`. It opens no listener, performs no live JWKS fetch, uses no owner data, installs no provider, and never holds privileged Supabase or OAuth credentials. The companion `tests/bp15_jwt_access_verifier.test.mjs` generates throwaway RSA keys in memory for synthetic tests.

## What this verifies

- **Purpose and signature:** RFC 9068 `typ=at+jwt` (or `application/at+jwt`), exact RS256-only algorithm allowlist, header limited to `alg`, `typ`, `kid`. Node's `crypto.verify` validates an RSA PKCS#1 v1.5 SHA-256 signature. No `none`, HS shared-secret fallback, untrusted `alg`, `jku`, `x5u`, `crit` or `b64:false`. The verifier never derives a key-fetch address from the token.
- **Issuer-bound keys:** an **injected trusted** `loadJwks({issuer})` callback returns the already-authenticated issuer's JWKS. Every key must have a unique bounded `kid`, and the selected public RSA JWK must declare `alg=RS256`, `use=sig`, exponent `AQAB`, optionally sole `key_ops=[verify]`, and at least a 2048-bit modulus; private JWK fields and unknown key properties are rejected. Up to 12 rotation keys are accepted; unknown/duplicate IDs fail closed. No unsigned or dynamically fetched JWKS is trusted by the module itself.
- **Bearer versus DPoP:** reject any JWT carrying a `cnf` confirmation claim on this Bearer-only verifier. Sender-constrained tokens need the future full RFC 9449 DPoP proof and access-token hash/key-thumbprint verification, not a silent downgrade to an ordinary Bearer.
- **Recipient and owner:** exact expected HTTPS `iss` and exact MCP `aud` (or a singleton equivalent), authenticated owner UUID `sub`, `role=authenticated`, `token_use=access`, bounded `client_id`/`jti`, and initially **only** `scope=tasks:read`. Reject ID tokens, service-role/anonymous/overprivileged tokens and multi-resource bearer substitution. The concrete issuer/resource identifiers are configuration inputs, not source-embedded Production URLs.
- **Freshness:** integer `iat` and `exp`, strictly unexpired, maximum 15-minute token lifetime, small 30-second future `iat` allowance, and `nbf` not in the future. Bounds also constrain compact JWS, segments, and key count. The module returns only claims after signature verification and all checks.
- **Live permission decision ports:** `isRevoked({issuer,subject,clientId,jti,scopes,expiresAt})` must resolve to boolean `false`, then `hasConsent(...)` must resolve to boolean `true` **on every access**. Missing hooks, network/database errors, undefined/truthy lookalikes, revoked IDs, or withdrawn scopes cause one non-reflective `MCP_TOKEN_DENIED`. These ports are **not implemented with in-memory production state**; a future durable server adapter must securely bind each owner/client/scope and verify its revocation store and token lifecycle.

The existing read boundary **still** independently restricts tool names, owner ID projection, arguments and output fields. Synthetic integration tests verify that a valid signed token does not let a caller provide an `ownerId` override, retrieve a foreign-owner row or call write/journal tools. This is **not** a complete RLS or two-account hosted database assessment.

## New atomic grant decision path (source-only)

The split `isRevoked`/`hasConsent` checks are retained for historical **offline** consumers. They do not provide transactionally coherent consent decisions when a grant is concurrently revoked or respecified. For any future hosted adapter, use the newly added **single** `authorizeGrant(context)` mode instead, backed by `createAtomicMcpGrantAuthorizer({readSnapshot})`. The signed token must carry `orbit_grant_id` and `orbit_grant_epoch`; the adapter's one coherent tenant-bound read verifies owner, issuer, client, resource, grant ID/epoch, exact scopes, consent freshness and token-JTI revocation. Missing store state or mixed split/atomic hook wiring denies before reads. See [BP15_ATOMIC_GRANTS.md](BP15_ATOMIC_GRANTS.md). None of this enables an OAuth connector or modifies a hosted database.

## Consent, revocation and key-rotation adapter design (not activated)

A future owner-controlled consent UI should enumerate exactly `tasks:read`, identified client, resource URI, expiration and revoke/disconnect consequences. Following explicit authorization-code + PKCE S256 and RFC 8707 `resource` in authorization **and** token requests, store a durable grant keyed by **issuer + subject UUID + client ID + resource** with allowed scopes, consent version, expiration and revocation timestamp. `hasConsent` must query the current committed grant (not trust the token's scope alone); revoking/disconnecting removes active grant and should revoke outstanding token `jti` values or enforce a per-client grant epoch. `isRevoked` must check issuer-scoped revocation state. Both hooks must be tenant-aware and fail closed, with bounded, audited non-sensitive logs and immediate revocation semantics verified before launch. Concurrent revoke/read consistency, outages, database RLS and replay windows need real adapter tests.

Bind the JWKS source to independently verified authorization-server metadata and a trusted HTTPS `jwks_uri`, with HTTPS/TLS, strict host allowlist, size/time limits, validated cache freshness and verified issuer. Do **not** allow a token's `kid`, `jku` or `x5u` to choose arbitrary network locations. During key rotation, temporarily accept the old and new distinct `kid` values only while policy permits; retire old keys after maximum issued token lifetime and a bounded cache grace. Reject unknown/duplicate kids, wrong algorithms, key type mismatch, and private JWK material. Never fall back to a different key on signature failure.

## Replay protection is not blanket bearer-token invalidation

Short-lived OAuth Bearer **access tokens are legitimately reusable** until expiration or revocation. Marking a `jti` consumed on the first ordinary MCP request would break valid repeated reads and is **not** an OAuth replay defense. The separate `createOneTimeProofGate` is a narrow coordination port for separately **cryptographically verified** one-time proof/state identifiers, with method/resource/issued-at binding and a required distributed **atomic** `consume(replayKey,{expiresAt})` adapter. It cannot verify DPoP proofs, HTTP signatures, OAuth authorization `state`, nonce, key-thumbprint binding or PKCE by itself. A future RFC 9449 DPoP deployment must verify the complete proof and token-binding semantics separately before calling this one-time guard. Avoid process-local sets in live multi-instance Vercel runtimes.

## Unfinished launch gates

- Explicit owner-approved OAuth/MCP resource URI and authorization server; OAuth 2.1 authorization code + PKCE S256, RFC 9728 protected-resource and RFC 8414 authorization-server metadata, client registration and redirect policy, state/nonce/CSRF validation, refresh-token rotation, privacy-conscious consent.
- Implement and independently test trusted JWKS metadata/rotation/cache adapter, durable grant/revocation backend, atomic proof replay storage, HTTP MCP transport, per-user RLS-delegated read queries and audit/rate limiting. **Never** use a global service-role database client for owner reads; never relay the MCP token to Supabase unchanged.
- Two real separate owner accounts, cross-tenant denial, signed-out/authentication failures, intentional revocation, consent withdrawal, key rotation and session recovery must pass in a protected, separately authorized environment before deployment or connector registration. W1 owns the actual repository/DB contract, W3 owns consent UI, W4 owns access-token/transport security.

All tests use generated synthetic keys and local adapters; successful source CI is neither a remotely connected OAuth provider nor a Production release. Rollback is a source PR revert, with **no** user-data or deployment migration.
