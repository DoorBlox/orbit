## Product decision: six is the current default, never a cap

ORBIT has **six core spatial widgets today** because that is how the existing V6 layout is instantiated, **not** because the owner requested a permanent six-window limit. Preserve those widgets, their identifiers, user coordinates, saved sizes, pan/zoom world, visual feel and original data, while enabling **more and different widgets**. Do not reject a seventh widget, alternate workspace, customizable widget placement or public-facing content merely because of an old "six-window" phrase.

**Stable identity:** a personal, navigable, spatial creative workspace where linked tasks, branches, writing, projects and attention coexist. A conventional fixed dashboard is not the goal, but an optional overview/launch surface and responsive alternative views are permissible. Do not interpret historical release-preservation text as veto power over future features. New widgets must remain discoverable, keyboard/touch reachable and performant offscreen; allow optional hiding/docking and recover-from-offscreen.

## Requested future experiences (not yet implemented)

1. **Projects inside ORBIT:** from any branch, use right-click **Turn into project**; also expose this command through a keyboard-accessible branch action menu (touch long-press optional). This is a **reversible semantic label**, not a destructive conversion or a new task tree. A Projects place/widget aggregates selected branches and their tasks, subtasks/subbranches, progress and context, with richer private project pages for descriptions, links, status, goals, notes and imagery. Keep original branch IDs, parent hierarchy, task IDs, positions and links unchanged. Project scope over descendants must be explicit and tested; duplicated/shared task counts must never mislead.
2. **Portfolio:** curate public project entries from private projects. A project being marked in ORBIT must **not** make its tasks, notes or files public. Explicitly choose public summary, screenshots, links, outcome and visibility, preview them, then publish a **separate reviewed public projection**. Later updates are explicit; withdrawing the public entry never deletes the private project.
3. **Blog from Journal:** private Journal page gets **Create blog draft** (or comparable wording). Copy only selected, sanitized text into a separate draft. Support editing headline/slug, excerpts, categories, cover image (only a specifically public copy), preview, **Publish**, revise, unpublish. No automatic exposure or sync of new private Journal edits, and never expose other diary entries, hidden metadata or private media paths by implication. A portfolio site can render published blog entries and published projects; the website is separate from the private ORBIT workspace.
4. **Pomodoro / Focus timer:** an optional movable Focus widget with start/pause/resume/reset, configurable work/break durations and an optional link to a task/project. No forced productivity scores or streaks. Use monotonic elapsed time plus persisted wall-clock timestamps for background/reload correction, not a per-second Supabase write. Notifications/sound require opt-in and browser permission. Provide reduced-motion and accessible keyboard/screen-reader behavior.

## Verified existing seams and implications

- `src/data.js` already represents **arbitrary-depth branches** and preserves IDs. `src/model.js` tasks refer to a branch via legacy `projectId` field; that name does **not** mean a full Project entity already exists.
- `src/constellation.js` already provides branch actions, and `src/app.js` mediates branch changes. Reuse them rather than fork task state. Right-click is an enhancement, **not the only input path**.
- `src/board.js` currently hardcodes six IDs in `DEFAULT`, `LIMITS`, and icon maps and creates widgets by iterating them. This is a **real source coupling to refactor**, carefully, before a seventh regular widget is safe. The existing six layout entries and saved sizes must roundtrip unchanged.
- `src/scene.js` validates `extensions` and currently bounds serialized data. New private project metadata must be validated, owner scoped and included in both normal JSON backups and the media-inclusive `.orbit` format, with old readers handled deliberately.
- `src/cloud/repository.js` currently has explicit `published_content` metadata projection (`id,kind,title,excerpt,published_date,updated_at`) and publish/unpublish RPCs. **It is not a blog-body publishing API.** A separate reviewed public-content contract is required for articles/projects; do not let anonymous clients fetch private snapshot or journal HTML. Any new hosted SQL/RLS/Storage/publish endpoint needs a separate approved migration and test plan.
- `src/journal.js` already has a sanitizer and Markdown export, which can seed a **drafting** pipeline, not authorize public release. Review text, links and asset handling for the website independently.
- Existing BP-03 snapshot reads/CAS and BP-02 portable backups remain safety gates. New UI should avoid writing cloud snapshots on every timer tick or rapidly changing animation state.
- ORBIT app currently uses native ES modules plus a **lazy isolated React Excalidraw island in source**. Neither Projects nor Pomodoro requires a React rewrite. For a future portfolio site, choose rendering/framework only after an explicit site brief; no imposed Next.js dependency.

## Product questions to refine during design, not blockers today

What qualifies as one project when nested branches exist? Should progress count only direct tasks or descendants by default? Should published portfolio pages use frozen snapshots or opt-in updates? What domain/brand and content style should the separate public site use? Should Focus session history exist at all? Keep sensible conservative defaults, leave these editable and do not impose them as an invented owner requirement.

## Security, cost, evidence, permissions

Private by default; public copies only by explicit confirmation. No anonymous SELECT to private tables or Storage, no service-role key in browsers, no disabling RLS. Validate URL and rich-text sanitization, cross-account isolation, slug ownership/collision, drafts, unpublish and deletion separately. Vercel/Supabase cost tuning needs real usage metrics; no speculative paid plan, third-party analytics, background service or custom domain changes. The currently native/static ORBIT frontend is **not** a supported app framework for the full Vercel Optimize route-to-file pipeline; do not present a metric-free code scan as that audit. New site technology and cost are future design choices.
